# 全社レビュー

会社の「やり方」を定期的に点検し、良くする。案件の中身の振り返りは各案件で行うので、ここでは扱わない。

## いつ使うか

- 定期: 月1回。定期実行にする場合は `management/automation/README.md` の手順で登録する(無人で動く)。
- 随時: オーナーに頼まれたとき、同じ種類のミス・手戻りが2回以上続いたとき。定期の回を待たずに行う。

## 実行してよい範囲

| 区分 | 内容 | 無人の定期実行 | オーナーと対話中 |
|---|---|---|---|
| 小さな変更 | lessons.md の統合・言い回しの修正、既存スキルの手順の誤りや古い記述の修正、tasks.md の整理、CLAUDE.md の記述を実態に合わせる | 実行してよい | 実行してよい |
| 構造の変更 | ファイル・フォルダの移動・改名・削除、新しいスキル・ルールの作成、スキルの統合・廃止 | **提案のみ** | 決裁権限(rules/04)に従う |
| 拡張機能 | プラグイン・MCP サーバー・外部スキルの導入・削除 | **提案のみ** | **オーナーの承認後に実行** |
| 定期実行 | `management/automation/` とタスクスケジューラの登録の変更 | **触らない(提案のみ)** | 承認後に実行 |

迷ったら「提案」に倒す。ルール 01〜04 の変更と記録の削除は、どの場合もオーナーの承認が必要(rules/04)。

## 手順

### 1. 材料を集める(対象: 前回のレビュー以降。初回は会社の立ち上げ以降)

- 前回のレビュー: `management/reviews/` の最新ファイル。提案がその後どうなったか(承認・却下・未回答)。
- オーナーとのやり取り: `communications/*.md`。オーナーに指摘・やり直しを頼まれた箇所、同じ説明を繰り返した箇所。
- `management/decisions.md`・`management/tasks.md`(期限切れ・止まっているタスク)・`organization/rules/lessons.md`。
- `git log --since=<前回の日付> --stat`: どのファイルがよく変わるか、まったく触られないか。
- 定期実行のログ: `%LOCALAPPDATA%\ai-company\logs\`(`exit=` が 0 以外の回)。
- 今ある仕組み: `.claude/skills/*/SKILL.md`・`.claude/agents/`・`.claude/settings.json`・CLAUDE.md、`claude plugin list` の出力。

### 2. 点検する

各項目で「事実(根拠のファイル・行)」と「判断」を分けて書く。

1. **運営**: オーナーの手間が増えた場面、同じミスの繰り返し、記録漏れ(rules/02 が守られているか)。
2. **ルール・教訓**: lessons.md に同じ趣旨の項目が重なっていないか。ルールにすべきなのにルールになっていない教訓はないか。CLAUDE.md が長すぎて読み落としが起きていないか。
3. **スキル**: 使われていないスキル(communications・git log に出てこない)、同じ手順を2回以上手でやったのにスキルになっていない仕事、description が曖昧で使われないスキル。
4. **フォルダ構成**: 置き場所のルールから外れたファイル、空のフォルダ。**移動を提案するときは、そのパスを参照している場所を `grep` で全部洗い出して提案に書く**(特に定期実行の手順書・スクリプト)。
5. **拡張機能**: 上の 1〜4 で見つけた困りごとを解決する拡張機能があるか調べる。困りごとがないのに入れる提案はしない(rules/01 #7)。評価の観点: 解決する具体的な困りごと / 提供元 / 会社のルールや手順とぶつからないか / 必要な権限 / 外し方。

### 3. 小さな変更を実施する

「実行してよい範囲」の小さな変更だけを行い、`/commit-push` の手順でコミットする(メッセージの頭は `全社レビュー:`)。

### 4. 報告書を書く

`management/reviews/YYYY-MM.md`(同じ月に2回目以降を行うときは `YYYY-MM-DD.md`)。

```markdown
# 全社レビュー YYYY-MM

- 実施日: YYYY-MM-DD(定期 / 随時)
- 対象期間: YYYY-MM-DD 〜 YYYY-MM-DD

## 結論
(3行以内。いちばん大事な改善を1つ)

## 前回の提案のその後

## 見つけたこと
| # | 区分 | 事実(根拠) | 判断 |

## 実施した変更
(コミットと変更したファイル)

## 提案(オーナーの判断待ち)
| # | 提案 | 理由・解決する困りごと | 影響範囲(参照しているパスなど) | やらない場合 | 推奨 |

## 見送ったもの
(検討したが入れなかった拡張機能などと、その理由)
```

### 5. オーナーへの引き継ぎ

- 提案が1件以上あれば、`management/tasks.md` の「CEO が進めるもの」に `全社レビュー YYYY-MM の提案をオーナーに確認する | CEO | 次の会話` を追加する(次の会話の開始時にフックで CEO に渡る)。
- 対話中に行った場合は、報告書の結論と提案を簡潔に伝え、`/owner-log` で記録する。承認された提案は `management/decisions.md` に記録してから実行し、報告書の提案の行に結果を追記する。

## チェックポイント

- 変更の数ではなく、オーナーの手間やミスがどれだけ減るかで提案を選んでいるか。提案は多くても5件まで。
- 提案はすべて根拠(ファイル・ログ・やり取り)を示しているか。
- 無人の回で、構造の変更・拡張機能の導入・定期実行の変更をしていないか。
